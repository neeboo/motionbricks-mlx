# 0004 · 采用"可证明逐位一致"的 f32 优化；量化继续关闭

**背景**：优化线把判据**先冻结再动手**（`docs/optimization-report.md` 第 0 节），逐项判定结果是
**一条都没采用**——包括"f32 全部优化合计 1.19×"。判据的性能门是 p50 ≥1.5× 或内存/冷启动 ≥2×。

## 决定

1. **f32 那组优化改为默认开启**（`MOTIONBRICKS_MLX_OPT` 默认 1）。
   **理由**：它通过了**正确性门的最高档**——5 组 seed × 6 步 **30/30 token 逐位一致**、
   `pose.sampling_uniforms` 逐元素一致、`mlx_align` plan/trace 仍 OK、默认路径产物**0 个值不同**；
   实测 p50 53.9→43.5 ms。性能门当初是为**挡住带风险的收益**，而零风险＋可证逐位一致属于另一类，
   所以这是**采纳决策，不是放宽判据**——判据本身一个字没改，报告里"否决"的结论仍然成立（它是在当时判据下判定）。
2. **量化默认关闭，且不得进入实时路径**。证据：q8 只有 **7/30** 步 token 一致、最差 roots 达容差的
   **2.2–25.6×**；q4 **0/30**、roots **30–91×**、3/6 步连时长都变了；`mlx_align` 对参考 **q8/q4 双双 FAIL**。
   内存收益是真的（791 MB → 222–230 MB，3.4–3.6×），但"改 token＝改动作"。
   **允许的唯一用途**：离线/批量烘焙，且**必须等 GLM 的动作质量评测门建立、并由该门判定动作可接受之后**才允许 q8（q4 不建议）。
3. **授权 host NumPy 向量化**：`src/motionbricks_mlx/data/agent.py` 属 A 侧（我），优化线当初没碰它是守规矩。
   下一步做：`build_constraints`（14.5 ms/步，其中 `_matrix_xyzw` 7.9 ms/182 次、`_cont6d_matrix` 4.9 ms/136 次，
   每次约 35 µs 而数组只有 3×3/34 关节——纯调用开销）。**要求**：与 `transition.py` 同款做法，
   验收仍是**逐位一致**（token 与最终动作），不是"误差更小"。
4. **批量化（B=2/4/8，吞吐 2.37×/3.12×/6.05×）**：暂不默认；它不改变单次延迟，且 B≥4 不再逐位。
   留给**批量烘焙**场景，届时以吞吐为主、逐位一致性为辅，并在报告里写明取舍。

## 诊断修正（记在案）

"慢在小算子派发"只对一半：拆成"建图 / `mx.eval`"后，**建图只占 2–8%，92–98% 是 GPU 上互相依赖的小 kernel**——
**真凶是串行依赖链**，`mx.compile` 只能碰那 2–8%。此外每步 55 ms 里 **19.9 ms（36%）在 host NumPy**，
所以"再快一档"的着力点是宿主侧与依赖链，而不是编译器开关。
