# 0009（已批准 2026-10-12）（提案） · 把运动解码批量化，并把它列为 release 烘焙配置的一部分

状态：**提案**，尚未批准。证据是 [optimization-report.md](../optimization-report.md) 第 43–49 节；
`docs/decisions/` 里的决定由人类裁定，本轮只写提案。

**触发**：第 5 轮把 2.29 ms/场景的未归因项留给了本轮，并写明"归因完成前不该优化它"。
本轮的直接仪器（每个叶子段一个 `perf_counter` 括号、各段之和与实测闭合到 0.9 %）把那个 2.29 拆开，
顺手暴露了一个比预期大得多的事实：**单趟烘焙里第二大的单项不是宿主算术，而是运动解码——
一个极小的设备图，被每个场景各自 drain 一次。**

## 测量（GPU，B=16 同构，9–15 次交错重复，load 11.4–14.8）

单趟烘焙每场景 7.948 ms，闭合分解：

| 段 | ms/场景 | 占比 |
|---|---|---|
| `eval`（4 个批量前向的 drain） | 3.4858 | 43.9 % |
| **`glue_decode`（`decode_motion` + 它的 drain）** | **2.0282** | **25.5 %** |
| `setup`（`constraints_for` 为主） | 0.7823 | 9.8 % |
| `collect`（`finish_plan`） | 0.3200 | 4.0 % |
| 其余宿主胶水（sample / pred_local / decoder_io / duration / …） | 1.331 | 16.7 % |
| 编排 + resume + 括号开销（闭合残差） | 0.073 | 0.9 % |

把 `glue_decode` 单独拿出来量：**建图 0.397 ms + drain 1.451 ms**，而同一台机器上一次
`mx.eval(mx.sum(x))` 是 **0.28–0.35 ms**。也就是说它是 launch/drain 受限，不是算术受限：

| B | 每场景一次 drain | 一次批量图 | 倍数 |
|---|---|---|---|
| 1 | 2.316 ms/场景 | 1.943 | 1.19× |
| 2 | 2.209 | 1.080 | 2.05× |
| 4 | 2.446 | 0.553 | 4.42× |
| 8 | 2.173 | 0.340 | 6.39× |
| 16 | 2.210 | 0.252 | 8.77× |

**配对前后**（同进程、同一批场景、顺序轮换；**每个 B 一个进程**，25 次重复）：

| B（同构） | 关闭 | 打开 | 配对 p50 | IQR | 逐位相同 |
|---|---|---|---|---|---|
| 4 | 12.683 | 12.311 | **1.0559×** | 0.935–1.207 | 是 |
| 8 | 9.417 | 8.124 | **1.1726×** | 1.007–1.326 | 是 |
| 16 | 8.136 | 6.677 | **1.2207×** | 1.132–1.335 | 是 |

端到端（9 次重复）：B=16 同构 **3.49–3.72× → 4.43–4.44×**（144–153 场景/秒），
B=8 同构 3.17–3.39×，B=16 混合 2.81–2.95×。**两臂 `compare_bitwise` 逐位相同**，
战役的 59–62 个场景 0 个 token 决策不同，裕度与第 5 轮**逐位相同**。

## 提案

1. **`bake_decode_batch` 采纳为正式开关，声明默认关闭**（与 `bake_root_batch` /
   `bake_decoder_batch` 同一规格）。它只对烘焙有意义，而且只对**单趟编排器**有意义：
   `batched_stages()` 里永远没有它，所以 `drive_batch`（round-4 对照臂）与
   `run_transition`（已验收单场景路径）一字未动，两个默认 sha256 不变。
2. **release 烘焙配置 = `--bake-stages all+decode`**（pose + root + decoder + decode）。
   档位结论不变：**混合 B ≤ 8、时长同构 B ≤ 16、B = 1 永不使用**（0007/0008）。
3. **B=1 不采用**：配对 0.9925×（中性偏负），与 0007 的"B=1 永不使用"一致。
4. **每件产物必须记 `bake_stage_switches` 含 `bake_decode_batch`**（已落地为
   `bake.manifest_fields`，0008 的档位规则同时落地：阈值 0.70、B>8 必须同构）。
5. **换权重 / 换指令分布 → 必须重跑战役并重算裕度**（沿用 0006/0007/0008）。
6. 附带纠正：第 5 轮报告的"宿主侧 3.97 ms/场景"里有约 2.0 ms 是**设备 drain**，
   不是宿主算术；批量解码之后，真正不可批的宿主侧约 **1.9 ms/场景**。
   下一次要动的顺序应是：`constraints_for`（0.64）与 `finish_plan`（0.32）之外的
   各个 drain，而不是"把宿主数学搬进图"——后者在 B=1 已被证否（报告第 13/46 节）。

## 验收要求（若批准，落地时必须复跑）

1. `scripts/mlx_bench.py --bake-stages all+decode --bake <B 列表> --bake-single-pass
   [--bake-homogeneous] --bake-repeats ≥5`：三臂端到端表 + 每 B 的 token 逐位率 +
   最终动作最差偏差 + 扰动/余量比；
2. `--bake-decode-paired`：配对前后 + 两臂逐位比较 + **每条臂解析后的开关值**（证明臂真的生效）；
3. `--bake-profile`：闭合分解表（含闭合残差）；
4. `pytest` 全绿且只增不减；`mlx_plan.py --device cpu --out …` 仍为 sha256 `262e77d4…`；
   `mlx_align plan/trace` 不回归。

## Lead 批准（2026-10-12）

**批准**。理由与边界：

1. 它**满足已冻结的采用判据**，没有新造：两臂 `compare_bitwise` 逐位相同、`mlx_align` 不回归、
   配对 ≥1.05×（B=8 **1.1726×**、B=16 **1.2207×**）；且**默认关闭**，只能被单趟编排器拥有
   （`batched_stages()` 永不含它），因此默认单场景路径与第三/四轮路径**一字未动**
   （GPU `ccda1952…`、CPU `262e77d4…` 复核一致）。
2. **release 烘焙配置确定为 `--bake-stages all+decode`**；档位结论**不变**：release = 混合 B ≤ 8 或时长同构 B ≤ 16，
   draft = 混合 B ≥ 16，**B = 1 永不使用**（该开关在 B=1 是 0.9925×）。
3. **一个使用限制写进文档**：B=4 的收益是边缘值（1.0559×，下四分位 0.935 跨过 1），
   所以**使用批量解码时建议 B ≥ 8**；B=4 只作可选项，且 manifest 必须记录配对 IQR
   （这条不改变档位，只约束用法）。
4. **方法学规则（本轮新发现，长期有效）**：跨 B 的配对**必须每个 B 单独进程**。
   同一长命进程里 B=8 曾量出 0.936×，独立进程重测为 1.1726×（profile 两臂亦证实 10.33→9.47）。
   长命进程会在 B 之间累积状态，使配对失真。
5. 回退路径照提案：不传 `--bake-stages all+decode` 即回到第五轮配置，其余数字（含裕度）逐位相同。
