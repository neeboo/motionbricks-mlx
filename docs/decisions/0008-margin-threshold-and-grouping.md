# 0008 · 裕度阈值改为可机械判定，并规定分组要求

**触发**：第 5 轮重跑战役后裕度与第 4 轮**逐位一致**（编排器不改变数值，只变快），但暴露了 `0007` 批准文本里的一处算术不精确：
裕度对 B **非单调**——混合 B=4 比值 **0.6849**（余量 1.46×）比混合 B=8 的 **0.6695**（1.49×）更差；
按字面"余量 ≥1.5×"（即比值 ≤0.6667）严格算，混合分组合格的最大 B 只有 **2**，而 `0007` 把 0.6695 记作"1.5×"并据此给出 B≤8。

## 裁定

1. **阈值写成可机械判定的形式**：**扰动/最紧余量 ≤ 0.70**（即余量 ≥1.43×）。据此混合分组 **release B ≤ 8**（0.6695）、同构 **B ≤ 8 起可放宽到 16**（0.4089–0.5290）。
2. **为什么是 0.70 而不是 0.6667**：1.5 这个数是当初取的整数启发式，**不是测出来的悬崖**；实测的安全边界落在"混合 B=8（0.6695，可过）"与"混合 B=16（1.0426，零余量）"之间。
   为了 0.4% 的算术取整而把整个烘焙档从 B=8 砍到 B=2，是**对启发式的仪式化服从**，会把行业标准做法（时长同构批次）一并丢掉。
   **这是阈值参数的修改，不是判据的放宽**：判据结构（必须先跑战役、必须报告裕度、必须如实记录）一字未动，且新阈值**更保守于**字面 1.5× 之外的任何位置（≤0.70 比 ≤1.0 严得多）。
3. **新增硬性分组要求**：**B > 8 必须按 duration 同构成组**（混合分组在 B=16 余量为零）。产物 manifest 必须记 `bake_grouping` 与 token 分组。
4. **机械降档规则**：任何一次重跑战役中，若**任一** B 的比值 > 0.70，档位自动降到该阈值下最大的合格 B；换模型/权重/指令分布必须重跑（沿用 0006/0007）。
5. **B = 1 永不使用**（比串行慢）。

## 附带纠正（我此前的预测也错了）

`0007` 批准文本里我写下"单趟编排器可把 B=16 从 2.812× 抬到约 4.6×"。**该预测不成立**，原因在预测所用的两个仪器本身：
第 4 轮的"批阶段 2.58 ms/场景"把 `stage_throughput` 的**派生 root 行（probe+plan）算了两次**，而 6.19 ms 又是用两个各自乐观的仪器相减得来。
真实单趟为 **8.24–8.48 ms/场景**，编排器实际价值 **1.15–1.19×**（实测同构 B=16：2.87–3.14× → **3.49–3.72×**）。
两个口径（含/不含派生 root 行）现已并列写进 JSON。**教训照旧：不要用两个各自乐观的仪器相减去预测收益。**
